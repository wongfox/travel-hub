# Known gaps behind the E2E suite (task 14.1)

The suite runs against an **in-process BFF** (`harness/in-process-stack.ts`,
see `README.md`), not the docker-compose stack: api and worker share one
process, one set of in-memory stores and the same stub adapters. Gaps A-C below
were found while writing the suite against the compose topology; they are
**resolved for E2E only** — the production wiring they describe is unchanged.
Last verified: Chromium, inside the Playwright image
(`e2e/scripts/run-in-docker.sh`): 20 passed, 0 skipped (scenario 5 now runs, gap D closed).

| Gap | What | Status |
|---|---|---|
| A | No black-box way to read an issued link's token | Resolved for E2E: the harness injects the stub `LinkDeliveryPort` and reads its `deliveries[]` in-process. A dev-only inspection route was explicitly rejected as a security risk; none exists. |
| B | Feature flags have no runtime override wiring | **Resolved for deployments.** `FEATURE_FLAG_OVERRIDES` (JSON object of known flag keys to booleans, e.g. `{"wifi.checkout":true}`) is parsed and validated by `loadEnv` (`config/env.ts`, `parseFlagOverrides` in `config/flags.ts`) and shared by `main-api.ts` and `main-worker.ts`; precedence is `FLAG_DEFAULTS` < overrides (defaults unchanged). Unknown keys, non-boolean values and malformed JSON fail at boot, and every override still passes the go-live guards (in production-like environments a flipped guarded flag with missing prerequisites fails boot in both processes). docker-compose forwards the variable (empty by default: `FEATURE_FLAG_OVERRIDES='{"wifi.checkout":true}' docker compose up -d --build`; from WSL with the Windows docker binary export `WSLENV=FEATURE_FLAG_OVERRIDES` too) and `infra/` plumbs `feature_flag_overrides`. The `feature_flag` table is not read (no reader; boot-time guards need synchronous config). Verified on compose: flag off `GET /api/wifi/packages` -> 403 `feature_disabled`; flag on -> 401 `link_expired` (module reachable, auth check). A full passenger flow on the compose stack is still blocked by gap A (no token-exposing route, deliberately). The harness still passes its own overrides in-process. |
| C | `bff-api` and `bff-worker` don't share in-memory stores | **Resolved for WiFi orders in the production topology**: both processes build the Postgres `WifiOrderStore` (`adapters/wifi-order-store/postgres.ts`, atomic compare-and-swap `transition`) from the same `DATABASE_URL`; compose runs a one-shot `bff-migrate` (`node dist/infra/db/migrate.js`) first (run the same command as a one-off task in production). Verified on the compose stack: an order created and paid through the API was activated, SIR-registered and receipted by the separate worker container. Resolved for E2E only for everything else (the harness shares in-memory store instances in one process). **Consent records and analytics events are now resolved in the production topology too**: both processes build the Postgres `ConsentStore` (`adapters/consent-store/postgres.ts`, append-only, latest wins by identity `seq`) and `AnalyticsEventStore` (`adapters/analytics-event-store/postgres.ts`, `analytics_event` holds only the pseudonymous `trip_hash`, all-or-nothing `createMany`, withdrawal cascade deletes pending rows) from the same `DATABASE_URL` (migrations 0002/0003 via `bff-migrate`; `consent_record.link_id` lost its `access_link` FK because access links are still in-memory). In production/staging `buildApp`/`startWorker` refuse to start without these shared stores. Verified on the compose stack by driving the real adapters/use cases over two separate Postgres pools (no token-exposing route, by design): consent and events written on the "api" pool were seen by the "worker" pool; a withdrawal deleted the pending rows; the deployed `bff-worker` container's `analytics-forward` job forwarded only the consented trip's rows and deleted the never-consented trip's. **Push subscriptions, notifications and the PII access audit are now resolved in the production topology as well:** both processes build the Postgres `PushSubscriptionStore` (`adapters/push-subscription-store/postgres.ts`; `link_id`/`consent_record_id` are uuid references without FKs because access links are still in-memory; indexes for the reservation/link lookups and the `expires_at` purge scan), `NotificationStore` (`adapters/notification-store/postgres.ts`; `UNIQUE(dedupe_key)` enforced by `INSERT ... ON CONFLICT DO NOTHING`, race-safe across processes) and `PiiAccessAuditPort` (`adapters/pii-access-audit/postgres.ts`; append-only, Postgres rejects UPDATE/DELETE with a trigger) from the same `DATABASE_URL` (migrations 0004-0006 via `bff-migrate`). In production/staging `buildApp`/`startWorker` refuse to start without the shared stores when the feature that uses them is on (`push.enabled`: subscription store, plus notification store in the worker; push/pulse/precheckin flags: shared audit). Verified on the compose stack over two separate Postgres pools (no token-exposing route): subscriptions, notification dedupe/status and audit rows written on the "api" pool were seen by the "worker" pool, the consent-withdrawal cascade deleted the subscriptions the worker pool then read, and the deployed `bff-worker` container processed a manually enqueued `push-subscription-purge` job (it deleted the 2 seeded expired subscriptions, kept the active one and wrote 2 `pii_access_audit` rows); a manually enqueued `journey-poll` job completed but is inert here because the SIR polling adapter still reads the in-memory access link store. **Pulse responses and staff alerts are now resolved in the production topology too:** both processes build the Postgres `PulseResponseStore` (`adapters/pulse-response-store/postgres.ts`; `UNIQUE(reservation_ref, passenger_ref, leg_ref)` via `INSERT ... ON CONFLICT DO NOTHING`, `purge_after` indexed) and `StaffAlertStore` (`adapters/staff-alert-store/postgres.ts`; `UNIQUE(pulse_response_id)` = exactly one alert per passenger/leg, race-safe across processes; `payload` is the strict minimal-PII `StaffAlertPayload`, validated by the adapter and by a DB CHECK that rejects any unexpected key; `pulse_response_id` has no FK so the independent purge scans and their audit rows keep working) from the same `DATABASE_URL` (migrations 0007/0008 via `bff-migrate`). In production/staging `buildApp`/`startWorker` refuse to start without them when `pulse.capture`/`pulse.staff_alerts` is on. Verified on the compose stack over two separate Postgres pools (duplicate submissions rejected and concurrent alert creates across both pools: exactly one winner; the worker pool saw the api's rows and the api pool the worker's status update) and with the deployed `bff-worker` container: manually enqueued `pulse-purge` and `pulse-staff-alert-dispatch` jobs completed, the expired response and expired alert were deleted with 2 `pii_access_audit` rows, and the pending alert was dispatched to the stub port (status `sent`, `dispatched_at` set). **Pre check-in submissions are now resolved in the production topology too:** both processes build the Postgres `PrecheckinSubmissionStore` (`adapters/precheckin-submission-store/postgres.ts`, migration 0009; the row holds METADATA and encrypted-document REFERENCES only: refs, doc type, consent record id, status, timestamps, object keys and the envelope-encryption material, never image bytes or plaintext; `UNIQUE(reservation_ref, passenger_ref)` via `INSERT ... ON CONFLICT DO NOTHING` is the race-safe `already_submitted` (409) guarantee and `submitPrecheckin` deletes the ciphertext it stored when it loses that race; `purge_after` only ever tightens and is indexed for the purge scan; crypto-shredding is also a DB CHECK; no FKs) from the same `DATABASE_URL`. In production/staging `buildApp`/`startWorker` refuse to start without it when `precheckin.production_collection` is on, and `main-api.ts` now passes the same env-derived retention config the worker uses. Verified on the compose stack over two separate Postgres pools (submission visible across pools, duplicate from the other pool rejected, 6 racing submissions across both pools: exactly one winner and one SQL row, handoff/purge visible both ways, no plaintext in the row) and with the deployed `bff-worker` container: a manually enqueued `precheckin-purge` job completed and purged the 2 due seeded submissions (key material zeroed, object keys kept, 2 `pii_access_audit` rows `worker:precheckin-purge-job`/`purge`), keeping the future one. **Still blocked: the real document/ciphertext store.** `PrecheckinDocumentStorePort` is still a per-process in-memory stub (object storage is a vendor integration, out of scope), so the api's ciphertext is invisible to the worker and the manually enqueued `precheckin-handoff` job `completed` while handing off NOTHING (it cannot read ciphertext; per-submission failures are swallowed by design, the submissions stay `received`, no `unwrap`/`handoff` audit rows); purge's object deletion is a no-op on the stub. `PrecheckinHandoffPort` is also still a stub. **Access links and sessions are now resolved in the production topology too:** `bff-api` (every instance) and `bff-worker` build the Postgres `AccessLinkStore` (`adapters/access-link-store/postgres.ts`; migration 0010) and, in the api, the Postgres `SessionStore` (`adapters/session-store/postgres.ts`) from the same `DATABASE_URL`. SECURITY: only the SHA-256 hex digest of a link token (`access_link.token_hash`, UNIQUE = the lookup index) and of a session id (`session.id_hash`, primary key) is stored: no column can hold a raw token or session id, and no token-exposing route exists. Expiry stays a use-case concern (`expiresAt <= now` is expired; both boundaries are tested on both store types); reissue now supersedes the previous links in ONE atomic step AFTER the new link is delivered (`supersedeOlderActive`: per-reservation advisory lock, keeps the newest link by identity `seq`, revokes every other active one with `superseded_by`; racing reissues across api instances converge to exactly one active link, and a failing delivery leaves the old link working); `access_link` has a CHECK that `superseded_by` implies `revoked_at`. `consent_record.link_id` and `push_subscription.link_id` deliberately STAY soft references (no FK): rows written while links were in-memory reference ids that never existed in `access_link` (the test DB holds 10 and 1 such rows), so an `ADD CONSTRAINT` would fail on existing data, and the purge/withdrawal jobs must not depend on link lifecycle. In production/staging `buildApp` refuses to start without both shared stores (always, not flag-gated) and `startWorker` refuses without the shared `accessLinkStore` when `push.enabled` is on and no explicit `journeyEventSource` is given (the existing `INTERNAL_LINKS_API_KEY` refusal and every go-live guard still win). Verified on the compose stack over two separate Postgres pools (a link issued on the "api" pool resolved by hash and appeared in `listActive` on the "worker" pool; a session created on one pool validated on the other; a reissue on one pool revoked the old link and its live sessions for both; 6 racing reissues across both pools left exactly one active link; 8 concurrent exchanges gave 8 independent sessions; 21 raw tokens/session ids never appeared in any stored column and every `token_hash` was a 64-char hex digest) and over HTTP against the real api container (`POST /internal/links` returned only `accessLinkId`/`expiresAt` and the row held only the hash; `POST /api/session` with a bogus token returned 401 `link_expired`, `POST /api/links/reissue` returned the uniform 202 for matching and non-matching inputs; the api/worker logs held no token). The deployed `bff-worker` container's manually enqueued `journey-poll` job `completed` but produced no notification: the stub SIR seed data departs beyond the default 48 h window (RES-2002's relocation is for 2026-11-03), so there is nothing to alert on today; run in-process against the compose DB with a 60-day window, the same job code now saw the api-issued link of RES-2002 through the Postgres store, found its RELOCATION event and pushed 1 notification (stub web push) to the seeded subscription (`notification` row `push`/`sent`/`RELOCATION`). **Still per-process (multi-instance gap):** the token-validation and reissue RATE LIMITERS (`createInMemoryRateLimiter`, a sliding window keyed by `request.ip` on `POST /api/session` and `POST /api/links/reissue`) keep their counters in each api process, so with N instances the effective limit is N times the configured max and a restart resets it; semantics deliberately unchanged here (moving them needs a shared atomic increment-and-expire counter, a separate decision). There is also no purge of expired `session` rows or of revoked/expired `access_link` rows yet (table growth only: expired sessions are rejected at read time). The push purge and journey-poll scans are not scheduled yet. **Analytics forward is now scheduled:** the worker enqueues `analytics-forward` every `ANALYTICS_FORWARD_INTERVAL_SECONDS` (default 60, positive integer) through the shared `scheduleQueueScans` helper (`sendIdempotent` natural key `scan`, send failures logged and retried next tick), only when the job is registered, and stops it on SIGTERM/SIGINT. Verified on the compose stack with a 3s interval: pending `analytics_event` rows of a consented trip got `forwarded_at` ~2s after insertion with no manual enqueue. **Open follow-up:** the other scans still have no scheduler, so they never run on their own in the production topology: precheckin handoff and purge, push dispatch, staff-alert (pulse) dispatch, `pulse-purge` and the remaining purge/retention jobs (their stores are shared now, only the scheduler calls are missing); each needs a `scheduleQueueScans` call in `main-worker.ts`. |
| D | No `PrecheckinPage`/route in `apps/web` | **Resolved.** `/trip/precheckin` (`PrecheckinPage`) is gated on `trip.features.precheckinCaptureUi` and the `consentTextVersions.precheckin` the BFF now publishes on `GET /api/trip` (from `PRECHECKIN_CONSENT_TEXT_VERSION`).
