# Program: Shared Postgres stores so the scheduled worker jobs actually work

## Objective
Every store read or written by a periodic worker scan job is Postgres-backed and shared by `bff-api` and `bff-worker` (same `DATABASE_URL`), so scheduling those jobs (final slice) has real effect in the production topology instead of running over per-process in-memory stores.

## Why
Branch 33's inventory (`odd/tasks/schedule-remaining-scans.md`, commit 941e122 on the scheduling branch) shows that precheckin handoff/purge, journey-poll, push-subscription purge, staff-alert dispatch and pulse purge read stores that are still in-memory per process. The user asked to make that work first, then schedule.

## Constraints
- No token-exposing route; no TLS weakening; no sudo; agents must not push or touch PRs; migrations must apply cleanly on top of the previous slices' (0001..0003).
- PII: stores must keep the existing minimal-PII shapes (`StaffAlertPayload.strict()`, no image bytes, no raw tokens); retention columns (`purge_after`, `expires_at`) indexed for the purge scans.
- Out of scope: real vendor adapters (object storage, web-push provider, staff-alert channel), changing job semantics.

### S3-T1 contracts (observed by reading the code)
- **PrecheckinSubmissionStore** (`modules/precheckin/ports.ts`): `findByPassenger(reservationRef, passengerRef)` (also feeds the `precheckinStatus` projection on `GET /api/trip`: none / received (received|handed_off) / unavailable (purged)), `create` (status `received`), `listPendingHandoff()` (`status = received`), `markHandedOff(id, handedOffAt, purgeAfter)` (flips status, tightens `purgeAfter`, never loosens), `listPastPurgeAfter(asOf)` (`purgeAfter <= asOf` and not purged), `markPurged(id, purgedAt)` (status purged + crypto-shred: key material zeroed, object keys kept as historical references). Unknown id throws on both mark methods. Writers: api `submitPrecheckin` (create); reader/writer: worker `precheckin-handoff` and `precheckin-purge` jobs (which write `pii_access_audit` unwrap/handoff/purge rows through the shared audit store of S1: untouched here).
- **What the record stores (verified: METADATA + encrypted-document REFERENCES only)**: reservation/passenger refs, `docType` (DNI|PASSPORT|OTHER), `consentRecordId`, status, timestamps, and per image (photo, id_front, optional id_back) `objectKey` + envelope-encryption material (`wrappedDataKey` = DEK wrapped by the KMS, `iv`, `authTag`). NO image bytes and NO plaintext document content ever reach this store: `submitPrecheckin` encrypts each image (fresh DEK per image) and puts the ciphertext in `PrecheckinDocumentStorePort`; only the wrapped DEK/iv/tag come back to the record. The Postgres table therefore stores no PII payload; the sensitive value is the wrapped DEK, which is useless without the KMS and is zeroed on purge.
- **`already_submitted` (409)**: today the use case does `findByPassenger` then `create`, and the in-memory `create` never rejects a duplicate, so two concurrent submissions for one passenger would both win. Decision: new table with `UNIQUE(reservation_ref, passenger_ref)` and a race-safe `INSERT ... ON CONFLICT DO NOTHING RETURNING`; `create` throws `AlreadySubmittedError` when no row comes back (the in-memory store now does the same, so the conformance suite holds for both). `http.ts` already maps `AlreadySubmittedError` to 409. Because the loser of a race has already put ciphertext in the document store, `submitPrecheckin` must delete those objects when `create` loses (otherwise orphaned, untracked ciphertext). A purged submission keeps its row (status `purged`), so the passenger stays `already_submitted` after purge, as in-memory today.
- **Retention**: `purgeAfter` is computed by the caller (`computeInitialPurgeAfter`, trip end + `PRECHECKIN_RETENTION_DAYS`) and tightened by the handoff job (`min(handed_off_at + HANDOFF_GRACE, ...)`, `retention.ts`). Decision: the store enforces "never loosen" itself (`purge_after = LEAST(purge_after, $new)` in SQL; in-memory uses `tightenPurgeAfter`) and refuses to hand off an already purged submission (key material shredded; also closes a purge-vs-handoff race that would otherwise flip a purged row back to `handed_off`). `purge_after` is indexed (partial, non-purged rows) for the purge scan; a partial index on `status = 'received'` serves the handoff scan; `seq` identity gives scan order. Boundary: `purgeAfter == asOf` is due.
- **Schema (no precheckin table exists from task 3.3, so a new table `precheckin_submission`, migration 0009)**: image envelope as flat columns (`photo_*`, `id_front_*`, `id_back_*`; bytea for `wrapped_data_key`/`iv`/`auth_tag`), `status` pg enum, `doc_type` pg enum, CHECK that a purged row has zeroed key material (defense in depth: crypto-shredding enforced by Postgres, not only by the adapter), CHECK that `id_back_*` is all-or-none. `consent_record_id` is text WITHOUT an FK (soft audit reference: the consent store is shared Postgres since branch 31 but this keeps the stores decoupled, same as S1/S2). No FK to the in-memory `access_link` (S4) and none to other tables: the handoff and purge scans are independent and must not be blocked by or cascade through other rows.
- **Out of scope / stays a stub**: `PrecheckinDocumentStorePort` (object storage / vendor adapter) and `PrecheckinHandoffPort`. ### S4-T1 contracts (observed by reading the code)
- **AccessLinkStore** (`modules/trip-access/access-link-store.ts`): `create`, `findByTokenHash`, `findById`, `findActiveByReservation` (`revokedAt IS NULL`, NO expiry filter), `revoke(id, supersededBy)`, `listActive()` (same, all reservations; the worker's SIR polling adapter calls it). Expiry is NOT a store concern: `exchangeAccessToken` rejects `link.expiresAt <= now` (boundary = expired) and `resolveActiveSession` rejects `session.expiresAt <= now`; the stores return rows unfiltered and round-trip `expiresAt` verbatim. Writers: api `POST /internal/links` (issue), `POST /api/links/reissue` (create + revoke); readers: api session exchange / `resolveActiveSession` (trip, privacy, precheckin, wifi, notifications, pulse routes via `findById`), worker `sir-polling` (`listActive`).
- **Only the SHA-256 hex digest is stored** (`hashAccessToken`, `access_link.token_hash text UNIQUE`); the raw token exists only in the issuance call (handed to `LinkDeliveryPort` and the link URL). Resolution is a hash lookup by unique index (the in-memory store does a `Map.get` on the hash, not a constant-time compare of secrets, so no constant-time requirement is dropped). The adapter never receives, logs or throws a raw token (errors carry ids/hash prefixes at most; decision: not even the hash in messages).
- **SessionStore** (`session-store.ts`): `create(idHash, {linkId, expiresAt, locale, userAgentClass})`, `findByIdHash`, `deleteByIdHash`. The session cookie value (`__Host-th_sess`) is a 32-byte random token, stored ONLY as `hashAccessToken(sessionId)` in `session.id_hash` (primary key): same design in-memory, followed exactly. Lifetime: `expiresAt = min(now + sessionSlidingMs, link.expiresAt)` computed ONCE by `exchangeAccessToken` (no sliding refresh exists: nothing updates `lastSeenAt`, there is no max-sessions-per-link cap, no purge of expired sessions); the store persists what it is given. `GET /api/session` and `resolveActiveSession` reject expired sessions (`<=`), and `resolveActiveSession` also rejects sessions whose link was revoked (so reissue kills live sessions of the old link immediately; the session ROW stays).
- **Reissue** (`reissue-link.ts`): reads `findActiveByReservation`, `issueAccessLink` (create + DELIVER), then revokes each previous link (`supersededBy` = new link) and deletes its push subscriptions. Decision: the use case keeps this order (a failing delivery must NOT revoke the passenger's still-working link, and a DB transaction must not stay open across an external delivery), so "insert new + mark old superseded" is not one SQL transaction. Instead the revoke step becomes ONE atomic statement under a per-reservation advisory lock: new port method `supersedeOlderActive(reservationRef)` keeps only the NEWEST active link (insertion `seq`) and revokes every other active link of the reservation with `superseded_by` = the newest, returning the revoked links (so the caller deletes their push subscriptions). Two concurrent reissues therefore converge to exactly one active link (the newest) whatever the interleaving, instead of both new links staying active (the previous snapshot-then-revoke logic left that gap). Sequential behavior is identical to today. `revoke` stays on the port; revoking an already revoked link keeps the FIRST revocation (never rewritten).
- **Schema (tables exist from task 3.3; migration 0010 extends them)**: `access_link` gets identity `seq` (total order for "newest", scan order), a partial index on `reservation_ref WHERE revoked_at IS NULL` (findActive/supersede) and a CHECK `superseded_by IS NULL OR revoked_at IS NOT NULL` (+ `superseded_by <> id`); `session` gets an index on `link_id` (FK lookups). `session.link_id` keeps its FK to `access_link` (sessions always reference a real link; the conformance harness provisions real links). `access_link.locale_hint` is unused by the port: left alone.
- **FK re-evaluation (`consent_record.link_id`, `push_subscription.link_id`)**: KEEP SOFT. Reasons: (1) rows written while access links were in-memory (every dev/staging DB so far) reference link ids that never existed in `access_link`, so `ADD CONSTRAINT` would fail on existing data (or need `NOT VALID`, which protects nothing for old rows); (2) the S1/S2 conformance suites and consent tests insert arbitrary uuids as `linkId`, they would all need real link rows; (3) purge/withdrawal jobs must be able to delete or keep these rows independently of link lifecycle. Evidence of orphans is recorded in S4-T5.
- **Rate limiter**: `createInMemoryRateLimiter` (`rate-limiter.ts`) is a per-process sliding-window array of hit timestamps keyed by `request.ip`, used by `POST /api/session` (token validation) and `POST /api/links/reissue`. With N api instances the effective limit is N x max and a restart resets it. NOT changed (default out of scope: moving it needs a shared counter store with an atomic increment-and-expire, a semantic/perf decision). Reported as a remaining multi-instance gap in KNOWN-GAPS.
- **Security tests that must stay green / get Postgres equivalents**: unknown/malformed/expired/revoked token never creates a session (`exchange-token.test`); reissue invalidates the previous token immediately (`reissue-link.test`, `session-http`); uniform 202 on reissue (`reissue-http.test`); link scoped to one reservation + passenger scope (`issue-link.test`); raw token never persisted (`issue-link.test`). The Postgres adapters run a shared flow suite (`trip-access-flow.conformance.ts`) over the REAL use cases with the same assertions, plus a Postgres-only dump of every stored row asserting no raw token/session id appears in any column.
